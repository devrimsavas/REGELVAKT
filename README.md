# Regelvakt

[![CI](https://github.com/devrimsavas/REGELVAKT/actions/workflows/ci.yml/badge.svg)](https://github.com/devrimsavas/REGELVAKT/actions/workflows/ci.yml)
Regelvakt shows small Norwegian businesses which official obligations apply to _their_ company, explains them in plain language, reminds them before deadlines, and answers questions with sources from official pages.

> Status: early development (pilot). Not tax or accounting advice.

## The problem

Small businesses struggle less with _doing_ their obligations than with _understanding_ which ones apply to them.

In Fiken's survey of small businesses (0–5 employees), the two hardest parts of running a business were:

- Finding and understanding information on sites like Skatteetaten and Altinn: **51.3 %**
- Annual accounts and the tax return: **43.2 %**

Source: [Fiken – Forenkling for næringslivet](https://www.regjeringen.no/contentassets/a4b761c84e654b65a0ec33085ad7530d/forenkling-for-naringslivet-_-rapport-fra-fiken.pdf)

## How it works

1. **Enter an organisation number.** Organisation form, VAT registration, employees, industry code and founding date are fetched from Brønnøysundregistrene.
2. **Answer a few short questions.** Questions depend on organisation form and VAT status (e.g. expected sales, payroll, expected profit).
3. **See "Your obligations".** Each obligation shows a short explanation, the next deadline, the official source and, where there is one, the service where it is filed.
4. **Ask a question.** An AI assistant answers from a knowledge base built on official pages and always cites its source.
5. **Get reminders.** Optional email reminders before deadlines.

### What it is not

Not an accounting system and not an accountant. Regelvakt does not file anything or keep books. It answers one question: _what applies to me, when, and what does it mean?_

## Rule engine (overview)

| Input                                                                    | Source                                                               |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Organisation form (ENK / AS), VAT registration, employees, industry code | Brønnøysundregistrene API                                            |
| Expected sales, payroll, expected profit, VAT term                       | Short questions to the user                                          |

## Tech stack

- **Backend:** Node.js, Express, TypeScript
- **Database:** PostgreSQL
- **Frontend:** Next.js, Designsystemet (Digdir), next-intl (Norwegian and English)
- **Email:** Resend
- **Hosting:** Docker, Cloudflare Tunnel

Shares its foundation (Brønnøysund integration, AI assistant, email) with [Leverandørvakt](https://leverandorvakt.devrimdev.no).

## Getting started (backend)

Requirements: Node.js 24 and a local PostgreSQL database.

Create `backend/.env` with these variables (`backend/env_example` also lists the optional logging, rate limit and proxy settings):

```
PORT=3000
DB_HOST=localhost
DB_PORT=5432
DB_NAME=regelvakt
DB_USER=postgres
DB_PASSWORD=
SUBSCRIPTION_SECRET=   # at least 32 random characters, see env_example
```

Then, in `backend/`:

```
npm install
npm run dev                  # compile, watch and run (applies pending migrations)
npm test                     # type check and run the tests
npm run lint                 # check formatting and lint rules (lint:fix fixes what it can)
npm run migrate -- pending   # list pending migrations (also: up, down, executed)
npm run reminders            # run the daily reminder work once, now
npm run knowledge            # read the official pages into the assistant's knowledge base now
npm run eval:assistant       # measure how often search finds a right page (after npm run knowledge)
npm run eval:answers         # ask the language model 11 questions and check the dates in its answers
```

## Getting started (web app)

Requirements: Node.js 24 and the API running (see above). In `web/`:

```
npm install
cp env_example .env.local    # API_URL, if the API is not at http://localhost:3000
npm run dev                  # http://localhost:3001
npm test                     # unit tests
npm run lint                 # ESLint with Next.js's rules
npm run typecheck
```

- The browser never calls the API. Pages and server actions call it from the Next.js server (`src/lib/api.ts`), passing on the visitor's address for the API's per-address limits and a request id that also appears in the API's log. So the API needs no public address and no CORS, and no key reaches the browser.
- The language is kept in a cookie, not in the address, because the links in the reminder emails carry none: a chosen language wins, otherwise the browser's, otherwise Norwegian.
- Light and dark mode follow the operating system until the user chooses; the choice is kept in a cookie, so the page is rendered in the right colors from the start.
- Every page gets a content security policy with a new nonce per request: only the page's own scripts run.
- `npm run theme` generates `src/theme` again after a change to `designsystemet.config.json`.

### End-to-end tests

`npm run e2e` in `web/` opens the web app in a real browser (Playwright) and goes through it as a user would: searching, the questions, every tab, changing the answers, the calendar, ordering, confirming, changing and stopping reminders (with the links read from the emails in the API's log), the one-click unsubscribe, the bot check, the assistant, deleting, the language and light/dark mode, and the menu on a phone. Every page is also checked with axe for WCAG 2.2 A and AA, in light and in dark mode, also with error messages shown.

It starts everything itself: the real API (built from `backend/`), the web app, and two stand-ins, one for Brønnøysundregistrene with fictional companies (`e2e/fakes/brreg.mjs`, reached through the API's `BRREG_API_URL`) and one for the language model (`e2e/fakes/ollama.mjs`), so every run sees the same companies and answers. Once:

```
createdb regelvakt_e2e           # an empty database; the API makes its tables
npx playwright install chromium  # the browser
```

Then, with the API built (`npm run build` in `backend/`):

```
npm run e2e
```

The tests use the database server, user and password of the API's own settings (`backend/.env`), with the database `regelvakt_e2e`; `E2E_DB_HOST`, `E2E_DB_PORT`, `E2E_DB_NAME`, `E2E_DB_USER` and `E2E_DB_PASSWORD` override them, and without `backend/.env` (as in CI) the defaults are localhost, 5432, postgres and postgres. Nothing else from `backend/.env` has an effect: the other settings are given in `playwright.config.ts`, and emails are only written to `web/e2e/.output/api.log`. If the API cannot start, its last log lines are shown. CI runs the same tests in the **e2e** job.

## Running with Docker

The web app, the API and the PostgreSQL database in three containers, the same on a laptop and on a server. In the repository root:

```
cp docker.env_example .env      # fill in DB_PASSWORD, SUBSCRIPTION_SECRET and the model settings
docker compose up -d --build
docker compose ps               # "healthy" once migrations have run and the database answers
docker compose logs -f api
```

- The web app answers at `http://127.0.0.1:3001` and the API at `http://127.0.0.1:3000` (Swagger at `/api/docs`, health at `/api/health`), from this machine only. On a server a Cloudflare tunnel or a reverse proxy in front of the web app is what the internet sees; the web app calls the API inside Docker, and PostgreSQL has no port outside Docker.
- The database lives in the `db-data` volume and survives `docker compose down`; only `down -v` deletes it.
- Migrations run when the API starts; the reminder job and the knowledge base update run inside it, so no cron is needed. On the first start the knowledge base is read from the official pages (a few minutes at one request a second).
- Assistant: `gemini` by default. For a local Ollama outside Docker, set `AI_PROVIDER=ollama` and `OLLAMA_HOST=http://host.docker.internal:11434`.
- Run a command in the running API, for example: `docker compose exec api node dist/runKnowledge.js`.
- The web image runs Next.js's standalone server (only the files it needs) as the `node` user; `/health` is its health check.
- The API image is built in two stages: TypeScript is compiled in the first, the second holds only the compiled code, the API docs and the production dependencies, and runs as the unprivileged `node` user. `docker stop` gives the app 40 seconds to finish running work.

## API

Interactive docs: `http://localhost:3000/api/docs` (generated by `npm run dev`).

| Endpoint                                  | Description                                                                                                                                           |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api`                                | API root                                                                                                                                              |
| `GET /api/health`                         | `{ status: "ok" }`, or 503 when the database is down (Docker health check, uptime monitors)                                                           |
| `GET /api/companies/:orgNumber`           | Company data from Brønnøysundregistrene in the app's own shape                                                                                        |
| `GET /api/companies/:orgNumber/questions` | The questions this company is asked before an assessment                                                                                              |
| `POST /api/assessments`                   | `{ orgNumber, answers }` → stored assessment with obligations, deadlines and warnings                                                                 |
| `GET /api/assessments/:id`                | A stored assessment, recalculated with today's date; `answersNeedUpdate` says when new company data needs new answers                                 |
| `GET /api/assessments/:id/questions`      | The questions for changing the answers, with the current answers (no Brreg call)                                                                      |
| `PATCH /api/assessments/:id`              | `{ answers }` → the assessment with new answers; subscriptions are kept                                                                               |
| `POST /api/assistant/ask`                 | `{ question, language?, assessmentId? }` → an answer with numbered sources (`mode: answer`), or the most relevant official sections (`mode: sources`) |
| `GET /api/assistant/status`               | Whether the knowledge base is ready, and which language model is used                                                                                 |
| `GET /api/assessments/:id/calendar.ics`   | The deadlines as a calendar to subscribe to (`?lang=nb\|en`)                                                                                          |
| `DELETE /api/assessments/:id`             | Delete an assessment with its reminders and email addresses                                                                                           |
| `POST /api/assessments/:id/subscriptions` | `{ email, language?, reminderDays?, consent: true }` → confirmation email (202, same answer for every address)                                        |
| `POST /api/subscriptions/confirm`         | `{ token }` from the confirmation email → active subscription and its `manageToken`                                                                   |
| `POST /api/subscriptions/lookup`          | `{ token }` (manage token) → the subscription                                                                                                         |
| `PATCH /api/subscriptions`                | `{ token, language?, reminderDays? }` → changed subscription                                                                                          |
| `POST /api/subscriptions/unsubscribe`     | `{ token }` → stops the reminders and deletes the address                                                                                             |

Errors: 400 invalid input (all problems listed), 404 company or assessment not found, 410 company struck off, 413 request body over 10 kb, 422 organization form not supported yet, 429 too many requests (with `retryAfterSeconds`), 502 Brreg unavailable.

Every response carries an `X-Request-Id` header; the same id is in the API's log lines for that request.

**Rule engine design**

- Rules live in code (versioned, unit tested); results are not stored but recalculated from the rules.
- The engine is a pure function: company + answers + today's date → result. No database or network access.
- _Facts_ combine Brreg data (organization form, VAT registration, employees as a hint) with answers (VAT term, expected sales, payroll, expected profit).
- Each _question_ carries the condition for when it is asked; each _obligation_ carries `appliesTo`, a human readable `reason`, a deadline schedule, a link to its official source and, where there is one, a link to where it is filed (`filingUrl`; `null` when it is filed from an accounting system).
- Deadline schedules: `annual`, `periodic` and `monthly`; deadlines on weekends and public holidays move to the next business day. A schedule marked `fixed` keeps its date: the annual accounts, where Brreg gives 31 July and a fee from 1 August without saying the deadline moves. An early reminder costs nothing; a late one can cost a fee.
- Supported organization forms are listed in the rules (first version: ENK and AS); other forms get a clear "not supported yet" result.
- `assessments` stores the organization number, a company snapshot, the answers and the rules version.

**Search quality** (`npm run eval:assistant`, 30 questions, a right page among the first five sources, 19–20 November 2026, before the link correction below)

| Search terms from                     | Found          | Time for 30 questions |
| ------------------------------------- | -------------- | --------------------- |
| The question itself (no model)        | 22 / 30 (73 %) | seconds               |
| `qwen3.8` 27B, local, half on the CPU | 25 / 30 (83 %) | about 18 minutes      |
| `gemma4:12b`, local, all on the GPU   | 26 / 30 (87 %) | under 5 minutes       |

All four misses with `gemma4:12b` were missing sources, not search: the annual accounts link in the rules led nowhere, and Lovdata does not allow automatic reading. Both are corrected in rules 2026.3.

**Answer quality** (`npm run eval:answers`: 11 questions, each with the dates a right answer must hold and the wrong ones it must not; three of them about a company, as of 20 November 2026; one with no answer in the sources, which must say so instead of guessing)

| Model and setting                                                             | Right answers   | Time                |
| ----------------------------------------------------------------------------- | --------------- | ------------------- |
| `gemma4:12b`, local, thinking on                                              | 8–9 / 10        | about 3 minutes     |
| `gemma4:12b`, local, thinking off                                             | 10 / 10 (100 %) | under half a minute |
| `gemma4:12b`, local, with the question about the next deadline (11 questions) | not run yet     |                     |

With thinking on, one question in each run came back empty, a different one each time. Ollama's own figures for it: a prompt of 2,707 tokens, then 5,482 tokens of "thinking" until the context window of 8,192 was full, and a stop for length before any answer was written. The assistant only reads the sources it is given and writes a few sentences, with the dates already worked out in [1], so the model is now asked not to think: no empty answers, the same answers otherwise, about seven times faster. An empty answer from Ollama is logged with those figures, and the assistant logs when it falls back to the sources because of one.

One check was too strict at first: the answer about a sole proprietorship's next VAT deadline gave its own date (10 December 2026, from [1]) and added that the pages give 10 March for businesses that have been granted the annual term. That is what the model is told to do with dates from the pages, so the check now fails only an answer that calls 10 March the company's next deadline.

**Rules as source [1]**

The first real question, "Når må jeg levere mva-meldingen?", got an answer that named only the annual term (10 March) and the agricultural one (10 April), not the common two-month deadlines. Search had found the right pages, but not the sections with the deadline table, and the model can only answer from what it is given. The deadlines were in Regelvakt's rules all along, checked against the official pages, so the rules are now a source of their own:

- Every obligation has two short texts in Norwegian and English: who it applies to, and all its deadlines in words. A test reads the dates out of each text and checks that they are exactly the dates of the obligation's schedule, for every combination of answers, so the text cannot drift from the dates the reminders and the calendar use.
- With an `assessmentId`, source [1] is that company: its obligations, why each applies, and its own dates for the next twelve months, already moved off weekends and holidays. The company's name is not sent to the model. Without one, source [1] lists every obligation with who it applies to and all its deadlines.
- The model is told to take dates and deadlines from [1] and explanations from the pages, to name every deadline that can apply, and to say so when a page gives another date than [1]. Sources carry `kind: "rules"` or `kind: "page"`.
- A date the rules moved off a weekend or a holiday carries the date it came from: "12. april 2027 (flyttet fra lørdag 10. april)". Without it, the model took the moved date and a page's own date for a contradiction, and the model is now told it is not one.
- With a company, [1] starts with its next six deadlines across all obligations, earliest first. Tested in the web app, "What is the next deadline?" got the VAT return's 10 December from the model, while the a-melding was due on 7 December: each obligation listed its own dates, and the model took the first obligation it read. An eleventh question in `npm run eval:answers` checks it.
- When no model answers, only the page sections are shown, as before: an excerpt of the rules would say less than the assessment page itself.
- Five page sections instead of six, and Ollama is asked for a context window of 8192 tokens: its default (2048 or 4096, depending on the version) cuts long sources off without telling.
- A Skatteetaten page with the two-month deadline table was looked for, to add to the knowledge base. Only third-party pages (banks, accounting firms) were found with the table. Skatteetaten has a deadline calendar, one tailored to each business after login, and a "Frister" API for accounting system vendors, but no page of theirs with the table could be found and checked. No unchecked page was added: the rules carry those dates instead.

**Assistant design**

- The model first turns the question into Norwegian search terms in the official wording, so questions in English or everyday words find the right pages. The question itself is always searched too.
- The model answers only from the sections it is given, marks each claim with its source number and says so when the sources do not answer the question. References to sources it was not given are removed.
- Search is full-text, not vector search: PostgreSQL's Norwegian stemming plus the model's search terms cover different wordings, there is no extra model to download or keep in step with the stored vectors, and search works the same with any language model or none.
- Text from the official pages is stored only to search in; answers are written in the model's own words with short excerpts and always link to the page.
- Before real users: a paid Gemini key (the free tier may use the questions to improve Google's products) and Skatteetaten's answer on reusing their guidance.

### Phase 4 – Reminders

- [x] Subscriptions with double opt-in: confirmation email, signed manage links, change and stop without an account, `List-Unsubscribe` one-click header
- [x] Email sending (`EMAIL_PROVIDER=log` or Resend), Norwegian and English templates
- [x] Deleting an assessment deletes its subscriptions and email addresses
- [x] Daily reminder job: reminders before deadlines, weekly Brreg refresh, clean-up of old data
- [x] Changing an assessment's answers without losing its subscriptions
- [x] Calendar subscription (iCalendar, RFC 5545) for Google Calendar, Outlook and Apple Calendar

**Reminder design**

- Reminders belong to an assessment; there are no user accounts.
- A subscription is `pending` until the link in the confirmation email is used; only `active` ones get reminders. Unconfirmed ones are deleted after 48 hours.
- Links in emails go to the web app, which calls the API with `POST`. Mail scanners open links on their own, so a `GET` link would confirm or stop reminders by itself.
- The confirmation token is random and stored only as a hash. The manage token is the subscription id signed with `SUBSCRIPTION_SECRET`, so every email can carry a working link without storing it.
- Unsubscribing deletes the subscription and the address. `reminder_deliveries` records what was sent, so a reminder is never sent twice.
- The reminder job runs daily at `EMAIL_HOUR` (07:00 Norwegian time by default), in three steps:
  1. Clean-up: unconfirmed subscriptions whose link has run out; assessments without any subscription that have not been used for 30 days: read, changed or fetched as a calendar (an ENK's snapshot holds the owner's name); records of reminders sent over a year ago.
  2. Refresh: company snapshots older than a week are fetched again from Brreg for assessments with reminders. When the new data makes the answers no longer fit (a newly VAT-registered company has not given its VAT term), the subscribers are asked once by email to answer again. A company gone from the register gets no more reminders; its subscribers are told and their addresses deleted.
  3. Send: a reminder is due when a deadline is at most that many days away and has not been reminded about. A missed day (server down) is caught up on the next run. Everything due for one subscriber goes in one email.
